Range Zip (a.k.a. Inappropriate Zip)

Introduction

Zip files are basically just some compressed data and metadata with byte offset pointers like so:

┏━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┓
┃ PK\3\4 Local file header 1  ┃<─╮
┃   2344 bytes                ┃  │
┃   chapter1.txt              ┃  │
┃   [compressed data]         ┃  │
┠─────────────────────────────┨  │
┃ ...                         ┃  │
┠─────────────────────────────┨  │
┃ PK\3\4 Local file header 2  ┃<─│─╮
┃   3210 bytes                ┃  │ │
┃   chapter2.txt              ┃  │ │
┃   [compressed data]         ┃  │ │
┠─────────────────────────────┨  │ │
┃ ...                         ┃  │ │
┠─────────────────────────────┨  │ │
┃ PK\1\2 Central dir header 1 ┃<─│─│─╮
┃   2344 bytes                ┃  │ │ │
┃   chapter1.txt offset───────╂──╯ │ │
┃ PK\1\2 Central dir header 2 ┃    │ │
┃   3210 bytes                ┃    │ │
┃   chapter2.txt offset───────╂────╯ │
┃ ...                         ┃      │
┠─────────────────────────────┨      │
┃ PK\5\6 End of central dir   ┃      │
┃   Central dir entry count   ┃      │
┃   Central dir size          ┃      │
┃   Central dir offset────────╂──────╯
┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┛

Since arbitrary bytes can appear before or between these blocks, I wondered if I could construct a file archiving different ranges of the same files.

Notice that 299798 ≪ 1050449; each book-N.txt is compressed and stored only once, but is referenced by 2-3 archive entries.

Description

The most important parts can be logically described as:

tale.zip
├── book-1.txt
├── book-2.txt
├── book-3.txt
├── book-1-2.zip
│   ├── book-1.txt
│   └── book-2.txt
└── book-2-3.zip
    ├── book-2.txt
    └── book-3.txt
And it gets larger when including book-[123].zip for completeness 
tale.zip
├── book-1.txt
├── book-2.txt
├── book-3.txt
├── book-1-2.zip
│   ├── book-1.txt
│   ├── book-2.txt
│   ├── book-1.zip
│   │   └── book-1.txt
│   └── book-2.zip
│       └── book-2.txt
├── book-2-3.zip
│   ├── book-2.txt
│   ├── book-3.txt
│   ├── book-2.zip
│   │   └── book-2.txt
│   └── book-3.zip
│       └── book-3.txt
├── book-1.zip
│   └── book-1.txt
├── book-2.zip
│   └── book-2.txt
└── book-3.zip
    └── book-3.txt

Notice that there is a general structure here, where this file could itself be "book-1-3.zip" of a larger archive.

The actual file bytes are laid out like this:

header 1-2.zip
header 1.zip
header 1.txt
data 1.txt
enddir 1.zip
header 2-3.zip
header 2.zip
header 2.txt
data 2.txt
enddir 2.zip
enddir 1-2.zip
header 3.zip
header 3.txt
data 3.txt
enddir 3.zip
enddir 2-3.zip
enddir tale.zip

(Where enddir means all Central Directory records of the file, and header is the local file header of a contained file, i.e. there is no "header tale.zip".)
You can see that e.g. header 2-3.zip is included inside 1-2.zip, but it is ignored there, and just a small number of bytes.

Endgame

So far, I have not been very critical of the construction, but there could be some concerns.

The ZIP specification states:

A ZIP file MUST have only one "end of central directory record".

However, the ZIP file format specification is famously unclear about what this (among other things) means exactly, considering:

  • It is perfectly rational to store a zip file inside another zip file
  • A zip file is allowed to contain arbitrary binary data both prefixing (self-extracting file) and following (file comment <64K) the archive data
  • Compressed data can happen to contain the EOCD signature bytes
  • Appending a new central directory to an archive is not unreasonable
  • So implementations vary

After performing my experiment, I found another similar use of overlapping byte ranges: A better zip bomb (recommended read!)

This actually led some applications to patch their implementations to reject such files, while others did not 🙂

Here's a patched example where listing and extracting the individual files is fine, but "extract all" and "test" fail:

$ unzip -v
UnZip 6.00 of 20 April 2009, by Debian. Original by Info-ZIP.

$ unzip -t tale.zip
Archive:  tale.zip
    testing: book-1.txt               OK
    testing: book-2.txt               OK
    testing: book-3.txt               OK
    testing: book-1.zip               OK
error: invalid zip file with overlapped components (possible zip bomb)

Maybe the file is a little bit inappropriate after all, but I still like it.
